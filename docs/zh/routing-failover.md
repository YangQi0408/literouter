## 核心架构定位

在 `literouter` 的工程设计中，**决策逻辑与网络通信严格分离**：

- `Router` 类（位于 `core/src/lr_router.cpp`）是一个纯状态机组件，不持有任何网络套接字或外部 I/O 句柄；
- 输入为客户端请求的逻辑模型名与各站点的当前健康状态，输出为排好序的候选链路数组（`Candidate`）；
- 纯逻辑设计保证了复杂的故障转移与权重计算具有 100% 可重复、可单测的确定性。

## 候选链生成算法 (Candidate Chain)

当客户端向代理发起对话、补全或嵌入请求时，`Router::candidatesFor(model)` 按照以下三阶段严格生成候选链路：

```text
客户端请求模型: "gpt-4o"
       │
       ▼
[阶段一: 显式路由匹配]
 检查 config.routes 中是否存在 model == "gpt-4o" 且 enabled == true ?
       ├── 是 ──▶ 严格依据 targets 数组顺序组装链路（尊重人工设定）
       │
       └── 否 ──▶ [阶段二: 全局自动透传]
                  检查 server.pass_through_unknown == true ?
                        ├── 是 ──▶ 扫描所有已启用的 providers
                        │          过滤出 models 列表中包含 "gpt-4o" 的站点
                        │          排序: priority 升序 -> weight 降序
                        │
                        └── 否 ──▶ [阶段三: 未匹配报错]
                                   立即返回 HTTP 404 model_not_found
```

### 阶段一：显式路由匹配 (Explicit Route)

若配置文件中明确声明了该模型的 `route`，例如：

```json
{
  "model": "gpt-4o",
  "enabled": true,
  "targets": [
    { "provider": "openai-direct", "model": "gpt-4o-2024-08-06" },
    { "provider": "azure-openai", "model": "gpt-4o-eastus" },
    { "provider": "backup-relay" }
  ]
}
```

1. 系统将**严格按照开发者定义的 `targets` 顺序**作为尝试序列；
2. **模型重命名映射**：如果目标项指定了 `model`（如 `gpt-4o-2024-08-06`），向上游发起请求时会将请求体中的模型名重写为上游物理模型名；若未指定则原样透传 `gpt-4o`。

### 阶段二：全局自动透传 (Pass-through)

当请求的模型不在 `routes` 中，但在服务端开启了 `pass_through_unknown: true`：

1. 扫描所有已启用（`enabled: true`）的中转站；
2. 筛选出其 `models` 列表中声明包含该逻辑模型名的中转站；
3. **确定性排序**：
   - 第一排序键：`priority` 升序（数值越小优先级越高，1 优于 10）；
   - 第二排序键：`weight` 降序（同一优先级下，权重越大越靠前）；
   - 熔断降级项后置（若启用了 `skip_open_circuits`）。

### 阶段三：未匹配处理 (404 Fallback)

若阶段一与阶段二均未找到任何可用中转站，代理立即返回标准 OpenAI 格式的 404 响应：

```json
{
  "error": {
    "message": "The model `xxx` does not exist or you do not have access to it.",
    "type": "invalid_request_error",
    "param": "model",
    "code": "model_not_found"
  }
}
```

## 响应头闸门 (Header Gate) 与无损故障转移

### 为什么流式请求需要“响应头闸门”？

在 Server-Sent Events (SSE) 流式对话场景中，如果不对故障转移的生命周期进行精确控制，极易发生灾难性串扰：

> **传统代理的典型缺陷**：某上游中转站输出了半句话（如 `"今天北京的天气是"`）后发生网络中断，此时代理若盲目切换到备用站点，备用站点会从头重新输出（如 `"你好！我是 AI 助手..."`），导致客户端接收到混杂扭曲的残缺文本。

为了从根本上杜绝该问题，`literouter` 引入了 **“响应头闸门 (Header Gate)”** 机制：

```text
客户端发起 SSE 流式请求
       │
       ▼
 尝试第 1 个候选站 (Provider A)
       │
       ├─▶ [未收到任何响应头 / 首包字节前] 发生错误 (超时 / 502 / 429)
       │   └── 闸门仍然开启 ──▶ 立即无缝切换至 Provider B (对客户端完全透明)
       │
       └─▶ [首包数据到达] ──▶ 向客户端发送 HTTP 200 与响应头
           └── 【响应头闸门立即永久关闭】
               └── 此时与 Provider A 绑定
                   └── 若随后发生网络断开，直接安全终止流，严禁切换到下一个节点！
```

### 重试状态码与故障判定矩阵

| 阶段 / 状态码 | 判定结果 | 是否触发故障转移 (Failover) | 处理策略 |
|---|---|:---:|---|
| **网络层错误** | 拒绝连接 / DNS 解析失败 / TLS 握手失败 / 连接超时 | ✅ **是** | 上游完全未处理请求，安全重试下一个站点 |
| **HTTP 408** | Request Timeout | ✅ **是** | 尝试下一个候选站点 |
| **HTTP 409 / 425** | Conflict / Too Early | ✅ **是** | 尝试下一个候选站点 |
| **HTTP 429** | Rate Limited (触发限流) | ✅ **是** | 当前站点额度耗尽或频控，自动降级至备用站 |
| **HTTP 500 ~ 599** | Internal Server Error / Bad Gateway / Unavailable | ✅ **是** | 上游崩溃或网关超时，立即无损故障转移 |
| **HTTP 400** | Bad Request (提示词语法错误/传参非法) | ❌ **否** | 属于客户端业务问题，直接透传返回给客户端 |
| **HTTP 401 / 403** | Unauthorized / Forbidden (Key 失效或 WAF 拦截) | ❌ **否** | 鉴权失败，直接返回，提示用户检查密钥 |
| **HTTP 404** | Not Found (上游无此端点或模型) | ❌ **否** | 直接返回给客户端 |
| **流式首包之后** | 响应头已写入客户端套接字后发生的任何异常 | ❌ **否** | **闸门关闭**，立即终止，杜绝双重回答拼接 |

## 熔断器工作机制 (Circuit Breaker)

为防止某个已经崩溃或欠费的上游中转站持续拖累整体请求的平均响应时间，每个中转站独立维护一个熔断状态机。

### 三状态机转换

```text
               连续失败 < 阈值
             ┌────────────────┐
             │                │
             ▼                │
     ┌──────────────┐   达到连续失败阈值   ┌──────────────┐
     │   Healthy    │ ─────────────────▶ │     Open     │
     │  (正常服务)   │                    │ (熔断冷却中)  │
     └──────────────┘                    └──────────────┘
             ▲                                  │
             │                                  │ 经过 circuit_cooldown_sec 秒
             │ 探测成功                          ▼
             │                           ┌──────────────┐
             └────────────────────────── │   Degraded   │
                         探测再次失败     │ (半开试探期)  │
                         ───────────────▶└──────────────┘
```

1. **Healthy (健康正常)**：所有请求正常优先分发；
2. **Open (熔断打开)**：当中转站连续遇到可重试故障达 `circuit_failure_threshold`（默认 3 次）时触发。
   - 在 `circuit_cooldown_sec`（默认 30 秒）冷却期内，该中转站会被降级移动至候选链的最末尾（若开启 `skip_open_circuits` 则直接略过）；
3. **Degraded (半开试探)**：冷却期结束后，状态自动转为降级试探态。
   - 下一个到达的请求将作为**探测探针 (Probe)** 放行给该站点；
   - 若探针请求成功，熔断器立即恢复为 **Healthy**，连续失败计数清零；
   - 若探针请求再次失败，立即重新跌回 **Open** 状态并重新开始 30 秒冷却。

### 纯粹性判定：杜绝误杀健康节点

在生产环境中，客户端行为可能导致虚假失败。`literouter` 做出了严格的纯粹性隔离：

- **客户端主动取消 (Client Abort)**：客户端在生成过程中关闭了网页或按下了停止按钮，HTTP 传输被客户端主动掐断，**绝不计入熔断失败**。
- **客户端业务错误 (HTTP 400)**：客户端发送了非法 JSON、不支持的参数或超出上下文长度的提示词，**绝不计入熔断失败**。

### 多节点全熔断兜底

如果极端情况下所有配置的中转站均处于熔断状态，`literouter` 不会简单直接拒绝服务，而是**挑出距离上次失败时间最久（冷却时间消耗最多）的中转站发起尝试**，为服务恢复保留最大的韧性与自愈机会。

## 重试预算控制 (`max_attempts`)

在配置项 `server.max_attempts` 中：
- 设为 `0`（默认）：遍历所有可用候选站点，直到有一个成功或全部失败；
- 设为 `N`（如 `2` 或 `3`）：单次请求最多只尝试前 `N` 个候选站点。超出预算后立即向上游报错，防止因庞大的候选链路导致客户端长时间挂起等待。
