# 个人自用与 API 分发

literouter 使用同一套路由、协议转换、熔断和流式转发服务两种场景。没有配置 `clients` 时，现有个人配置继续生效；需要分发时，添加客户端账户即可，不需要切换运行模式。

## 管理员与客户端

`server.api_key` 是管理员密钥，也可用于管理员自己的模型调用。配置任何客户端后，它必须非空。客户端的密钥只能访问模型接口，不能读取管理配置、日志、指标，或执行重载、清空统计、关闭服务。静态控制台和健康检查仍可以匿名加载；控制台的数据需要管理员密钥。

一个客户端可有多把独立启停的密钥，所有密钥共享账户权限、并发和配额。账户停用后，其全部密钥立即停止接收新请求。已经开始的请求会正常结束并结算。删除账户不会删除配额历史，以同一个 ID 重建账户会继续使用已有用量。

密钥支持 `${ENV_VAR}` 引用。带默认值的 `${VAR:-fallback}` 可能包含真实凭据，管理接口会像明文密钥一样将其隐藏，保存时仍保留原始引用。管理 API 对服务器、上游和客户端的明文密钥全部脱敏；编辑未改动的空白密钥会保留旧值，`api_key_clear: true` 才明确清空。客户端密钥按“客户端 ID + 密钥 ID”匹配，因此修改 ID 时需要重新提供密钥。启用的密钥不能为空，管理员密钥也不能在仍有客户端时清空。密钥或环境变量解析结果重复时拒绝鉴权，不选择任意账户。

## 示例

这是分发配置的最小示例；未列出的服务器和中转站字段使用原有默认值。

```json
{
  "server": {"host": "127.0.0.1", "port": 8787, "api_key": "${LITEROUTER_ADMIN_KEY}"},
  "providers": [{
    "id": "relay", "base_url": "https://api.example.com/v1", "api_key": "${RELAY_KEY}",
    "groups": ["team"], "models": ["gpt-4o"]
  }],
  "routes": [{"model": "assistant", "targets": [{"provider": "relay", "model": "gpt-4o"}]}],
  "clients": [{
    "id": "team-a", "name": "团队 A", "enabled": true,
    "keys": [{"id": "desktop", "api_key": "${TEAM_A_KEY}", "enabled": true}],
    "models": ["assistant"], "provider_groups": ["team"],
    "requests_per_minute": 60, "max_concurrent": 4,
    "requests_per_day": 1000, "tokens_per_day": 1000000, "token_reservation": 4096
  }]
}
```

客户端携带自己的 `Authorization: Bearer <key>` 或 `x-api-key` 调用原有模型接口。`models` 匹配客户端请求的逻辑模型名，不是重命名后的上游名。`provider_groups` 与中转站的 `groups` 有任一交集即可使用该站。两个列表分别为空时，表示不限制该维度。只有权限内的站会参与排序、会话亲和、重试和故障转移；不会在全部失败后降级到权限外的站。

客户端读取模型列表时，只能看到同时满足模型权限和渠道权限的模型，也不会收到内部路由目标信息。管理员仍看到完整列表。权限拒绝返回 `403`，无可用候选返回 `404`，无效或停用的密钥返回 `401`。

## 配额语义

| 配置 | 语义 |
|---|---|
| `requests_per_minute` | 滚动 60 秒内允许接纳的请求数；0 不限制。 |
| `max_concurrent` | 同时在途的请求数，包含等待首包和整个流式响应；0 不限制。 |
| `requests_per_day` | UTC 当天接纳的请求数；0 不限制。上游失败也算一次，重试不重复计请求。 |
| `tokens_per_day` | UTC 当天 Token 预算；0 不限制。依据上游报告的输入与输出 Token 结算。 |
| `token_reservation` | 有 Token 配额时，每请求预留的最小额度，默认 4096；必须大于 0 且不超过日额度。 |

日配额和 Token 预留值必须是 0 到 9007199254740991 的整数，以确保 CLI、GUI、Web 和配置文件精确往返。RPM 与并发数的上限是 2147483647。

请求在向上游发出之前，原子检查并预留额度，避免并发请求各自看到相同余额。预留量取配置值与请求中输入字节、显式输出上限估计值的较大者；这是保守的准入预算，并非某一种模型的分词器。完整用量到达后释放预留并扣除实际 Token。未报告用量、流中断或进程崩溃时保留预留，避免未计量流免费消耗服务。

Token 配额不是模型侧的硬输出限制。上游的实际用量超过预留时会全额记账，累计可能由这次响应超过额度，之后的新请求被拒绝；流中断时按预留值和已观察到的部分用量中较大者记账。应按工作负载设置足够的预留，尤其是多模态请求。没有上游用量时，展示的“报告 Token”保持真实的 0，“今日计费额度”包含保留的预留值。

限流或额度不足返回 `429` 和 `Retry-After`。配额状态位于 `LITEROUTER_STATE_DIR` 下的 `clients-config-<hash>.json`，其中 `<hash>` 是规范化绝对配置路径的完整 SHA-256。在准入和结算时原子写入，独立于 `server.persist_telemetry`；重启、更改监听端口（包括随机端口）、清空日志和重置遥测都不会重置配额。请保持配置路径和状态目录稳定，并使用持久存储。不同配置使用独立账本。直接调用核心库且未设置配置路径时，使用 `clients-<port>.json`。

同目录的 `.json.lock` 文件通过操作系统锁保证账本只有一个所有者。配置了客户端的实例遇到其他进程占用账本或账本损坏时拒绝启动；实例停止或崩溃后锁自动释放，锁文件可以保留。没有客户端且没有已有账本的个人实例不会创建配额或锁文件；后续启用客户端时，在接纳请求前获取账本所有权。运行中无法获取所有权或保存预留时返回 `503`，恢复正确文件或存储后重启服务，不要通过删除文件处理额度不足。

日额度按 UTC 零点更新；跨零点的请求归属于接纳当天，同时继续占用并发槽位。按客户端统计的请求、成功、失败、输入/输出 Token、估算成本与当前配额通过管理员状态接口的 `clients` 数组提供。成本使用现有中转站价目表，未配置价格不产生估算费用。

## 管理与部署

CLI、GUI 和 Web 提供客户端、密钥、模型/组权限及额度管理。请求日志包含 `client_id` 与 `client_key_id`，不包含鉴权凭据。Prometheus 指标新增按 `client` 标签区分的请求、Token、估算成本、在途请求及当天额度数据，仍仅允许管理员读取。

可通过监听侧 TLS 或可信反向代理部署 HTTPS。对外分发前设置管理员密钥和独立客户端密钥；个人自用无需增加账户。充值支付、公开注册与新的上游协议不属于此功能。

### 部署方式

仓库提供四种落地方式，选择哪一种取决于这台机器上有什么：

| 方式 | 文件 | 适用 |
|---|---|---|
| 直接跑二进制 | `scripts/install.sh` | 一台长期在线的机器；脚本会校验发布包的 SHA-256，并可选地装好 systemd 单元 |
| systemd 服务 | `deploy/literouter.service` | 用发行版自带的服务管理；独立账户、`ProtectSystem=strict`、`SIGTERM` 优雅停机 |
| Docker | `Dockerfile` | 容器化主机。多阶段构建，运行镜像只装 `ca-certificates` 与一个二进制，以 uid 8787 非 root 运行 |
| Docker Compose | `docker-compose.yml` | 需要把配置与状态分开持久化的场景 |

两条与运维有关的注意事项：

- **配置与状态必须分开挂载。** 配置（`/etc/literouter`）里有密钥，是你编辑和备份的对象；状态目录（`/var/lib/literouter`）里是遥测文件与**客户端配额账本**。把账本放在匿名卷上，等于每次 `docker compose down -v` 都给所有客户端重发一天的配额。
- **容器里的监听地址是 `0.0.0.0`，端口映射请绑到宿主机回环**（`-p 127.0.0.1:8787:8787`）。`/ui` 控制台能读请求日志，而请求日志可能包含提示词；把它暴露到 0.0.0.0 且不设 `server.api_key` 时，校验器会给出警告，但那应该是一个刻意的决定，而不是从 compose 文件里继承来的默认值。

**改端口时改配置文件，不要改 `docker run`。** 容器的 `CMD` 只钉住了 `--host 0.0.0.0`（否则会监听容器内的回环，映射出去的端口没人应答），端口留给配置文件的 `server.port`。也就是说容器里的 `server.port` 和本机运行时含义一致：

```bash
# 配置写 server.port = 9000，就发布 9000
docker run -p 127.0.0.1:9000:9000 …
```

`EXPOSE 8787` 只是文档性声明，不决定实际监听端口。健康检查 `literouter status` 读的是同一份配置，因此会自动跟着 `server.port` 走，不需要同步修改。

健康检查用 `literouter status --json --quiet`：它走的是与客户端同一条管理 API 路径，因此检查的是「监听器 + 配置 + 管理面」这一整条链路，而不只是「进程还在不在」。就绪与存活的区别见[协议与 API](protocols-api.md)。
